# Desktop Pet v0.4.13 release notes

Status: **Stable publication explicitly authorized by the owner after local verification, without the unavailable disposable-GUI qualification.** Publication is not evidence of successful beta.7 recovery, native consent, original-profile restart or Tern reconnection. The qualification limits below remain unresolved.

## App-only update from beta.7, then a separate location approval

The intended entry point is the **Update button in the genuine installed 0.4.13-beta.7 app**. Its unchanged bundled updater can select a genuine newer Stable 0.4.13; publishing another beta cannot repair that updater's Stable-only admission. The first transaction must finish installing and starting 0.4.13 at the original OS-account-home `Applications/DesktopPet.app`, including the old helper's readiness check, Completed result, helper exit and release of its reservations. No installer or terminal bootstrap is part of this route.

Only after that transaction has settled may a new native panel ask **a second, independent approval** to move the same signed 0.4.13 app to the OS-account-home `.local/share/desktop-pet/libexec/DesktopPet.app`. The first update approval is not relocation consent. The panel must show the actual source/destination and original config/state paths, explain that only Desktop Pet restarts, and ask the user to save unsaved Pet edits. Cancelling leaves 0.4.13 running at the original location; the same automatic offer must not recur after restart. A later explicit Updates action requires a fresh approval.

The original Applications location remains recognizable for old-helper completion, relocation and recovery, not as a permanent normal-update destination. After successful relocation no app, alias, symlink or launcher remains there. A private retained original and its signed sidecar remain as transaction evidence. A second unexplained private installation or sidecar, an unsafe owner/path, cross-device original retention, changed Stop generation or ambiguous ACK must fail closed rather than overwrite, force-stop or silently restart.

## Preserve the exact profile and running Tern work

The move preserves the authenticated original config/state pair, selected character, settings and user data; it does not create a replacement default profile. Destination paths come from the OS account home, not a substituted HOME/XDG string. Stop applies only to the original Pet instance, and a deliberate later user Stop remains authoritative.

Tern, its actual windows, terminals and ongoing work must remain running. The existing qualified Tern SDK consumer uses its guarded saved-route update to change **only the executable** to the private app while keeping the same config/state. Production plugin bytes and pins are unchanged; no plugin reload, Configure/Connect reset, Tern restart or native direct KV rewrite may conceal a continuity failure. Native installation success and Tern integration confirmation are separate outcomes: an absent live binding or unavailable/incompatible consumer is integration pending, not evidence that the native update failed or that a window reconnected.

Each observed window needs its own fresh post-save receipt against the current private native instance. Protocol window IDs can change when the existing consumer resets identity; ID equality across that reset is not required or claimed as cryptographic window continuity. Actual two-window/work continuity must also be observed end to end. Route repair after a native restart or later canonical update must authenticate settled historical transaction/owner-chain evidence, rather than pinning success permanently to the initial relocated instance.

## Qualification limits and required release order

The genuine public beta.7 binary was previously inspected read-only for version, capabilities, signature and signed closure; that is **not a live beta.7 update**. Local checks passed: TypeScript, 62 Bun tooling/rig tests, the native workspace suite (one ignored test), additional app-update regressions, legacy shared-contract compilation with its pinned migration revision, and neutral arm64 build/package. The packaged app passed deep/strict codesign, exact complete 72-file deployed SHA-256 closure, and actual app/helper version/identity/capability execution. Actual CLI smoke read historical v1/v2 observations and rejected forged relocation authority. Behavioral regressions reproduced and fixed cancelled-result observation/settlement and rolled-back owner-chain failures. The isolated HTTPS fixture served six synthetic payloads with certificate/hostname verification and rejected foreign Host/traversal/unknown routes; this is transport smoke, not final-draft or GUI qualification.

Tern challenge and receipt evidence uses a guarded private `install-{id}.tern-relocation/` directory. The originally proposed flat names exceeded macOS's 255-byte basename limit; nesting preserves every full image/instance/tuple/window digest and leaves the SDK wire unchanged. Atomic publication uses an independent short temporary basename and never removes a published final receipt on later sync failure.

A usable authorized, logged-in disposable macOS arm64 VM with actual Tern windows is not currently available: virtualization commands were absent, no tool-managed SSH host was configured, and the configured remote SSH attempt failed because its identity file was missing and authentication was denied. The host's existing user installation is not a disposable qualification target and must not be modified. Consequently no native dialog rendering, two-stage update, original-profile preservation, two-window/work continuity, disconnected-binding recovery, cancellation persistence or future-update GUI success is claimed.

The owner explicitly authorized release publication despite the unavailable disposable-VM gate. CI must still build the immutable tag, pass source/package gates, and create six draft assets; those exact assets must be downloaded and verified before promotion. The unmodified beta.7 connected/disconnected two-window scenarios, second-consent cancellation, four-locale rendering and unpublished 0.4.14-beta.1 future-update fixture have **not** been exercised. A transport fixture is not official-network or GUI qualification and must never change host/user DNS or trust.

After publication, a clean beta.7 baseline without fixture DNS/CA is still needed to exercise the actual user path over official GitHub HTTPS. Wiki publication is separate and must use the exact published release. If frozen source/bytes need correction, preserve the existing tag/assets and use the next unused stable patch. Until all acceptance observations exist, **do not report affected-user recovery or release qualification complete**.
