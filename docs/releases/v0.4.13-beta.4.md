# Desktop Pet v0.4.13-beta.4 release notes

Status: **Beta prerelease — opt-in experimental source delivery, not proven recovery or a new stable release.** This candidate follows published [v0.4.13-beta.3](https://github.com/hanbong5938/desktop-pet/releases/tag/v0.4.13-beta.3). Stable `0.4.12` remains the latest stable release and the authorized migration target. These notes do not assert publication, successful recovery, or new migration permission.

## Changes

- Preserve beta.3's canonical neutral `v`-prefixed beta discovery and candidate/checksum revalidation, immutable migration-plan authority with separately selected live profile observations, and completed migration history that does not mask current update checks, errors, details, or actions.
- The **only new functional change** is bundling the existing immutable Tern deadline correction. Both the bundled consumer and native adapter dependency move from `69696023e00a0fcda8b85b332a075bfa26d6c26d` to exact public revision [`7276c1b658a1728883d90207119df31bce118170`](https://github.com/hanbong5938/tern-desktop-pet/commit/7276c1b658a1728883d90207119df31bce118170). The plugin version stays `0.2.1`; packaging still verifies immutable source digests and agreement between the consumer, adapter, and lockfile pins.
- Only migration-route authority (`resolve_migration` / `legacy-migration-route`) and handover authority (`handover_process` / `migration-integration-handover`) use **60,000 ms**. Ordinary discovery, installation proof, capabilities, and profile setup retain **10,000 ms**; normal exchange retains **2,600 ms**. This is not a global timeout increase.

Validation, errors and error wording, retry cadence, notification policy, signatures, original approval, exact profile/instance/image identity, Stop fences, fresh same-window binding, and native receipt authority are unchanged. A timeout or stale/mismatched handover still fails closed. The correction neither suppresses failures nor guarantees completion within 60 seconds.

Beta update entries remain **Download, not Apply**. Beta consent does not install or restart the app, grant automatic beta installation, or qualify a legacy migration route. Existing installation-owner and updater-reservation boundaries remain enforced.

## Scope and compatibility

The neutral app, Core package, and paired update coordinator are product version `0.4.13-beta.4`. Shared contracts remain `0.1.0`; the legacy bridge remains `0.3.16`, with no new bridge release. Protocol **4**, observation capability **2**, integration API **1**, and migration handover protocol **1** are unchanged. Product identity remains `DesktopPet.app`, `io.github.hanbong5938.desktop-pet`, and `desktop-pet` / `desktop-pet-update-coordinator`.

`MIGRATION_TARGET_VERSION` remains `0.4.12`. Beta.3's discovery/history corrections and earlier beta UI improvements are retained; this release does not change provider selection, session routing, connection protocols, or migration authorization. Existing stable and beta.1/.2/.3 tags, assets, and release notes remain immutable. No stable/main-channel, Homebrew, or wiki rollout is included.

## Prior source evidence — not final beta.4 validation

The following evidence belongs to the earlier **beta.2-based corrected source**, before this beta.4 cutover. It is not final beta.4 native validation, tagged-source packaging evidence, or proof about published beta.4 bytes:

- TypeScript checking, **65 Bun tests**, the full native suite, and the main-thread AppKit harness passed. The Tern working-copy native adapter suite passed **42 tests**; this is working-copy evidence, not a new immutable-source qualification claim.
- A real signed-in **Tern 0.9.4** ran production Luau through controlled SDK boundaries: old immutable consumer source passed **199/200** cases; corrected source passed **200/200**. Migration authority and handover each succeeded with **16,000 ms** controlled delay. Separate **60,001 ms** cases failed closed and recovered through the existing polling/fresh-binding path after the delay was removed. Four ordinary metadata stages—discovery, proof, capabilities, and profile—each failed at **10,001 ms**, without activating exchange or saving a route, and were not automatically retried as new setup on the next ordinary poll.
- Local corrected-source staging and ad-hoc bundle signature verification succeeded. **Ad-hoc signing is not Developer ID signing or notarization**, and local staging does not establish official CI provenance or successful installation/handover.

These controlled delays test boundary behavior; they are **not measured real SDK authority wall times**. Beta.3's separate discovery/history evidence remains recorded in the [beta.3 notes](v0.4.13-beta.3.md), not relabeled as beta.4 evidence.

## Final local beta.4 candidate verification

After the beta.4 metadata and consumer-pin cutover, release-note/product-metadata admission, TypeScript checking, **65 Bun tests / 767 expectations**, Rust formatting, shell syntax, and the complete default-parallel arm64 native workspace suite passed. Native results included **652 Core tests passed / 1 ignored**, **140 coordinator library tests**, **23 helper tests**, the other workspace suites, and the actual main-thread AppKit composer harness. Installer help reported the exact beta.4 version.

The isolated `--source --stage-only` path completed optimized native build, immutable consumer download/digest admission, native rig validation, and packaging without installing or replacing an app. Deep/strict signature verification passed; app and helper both reported **0.4.13-beta.4**, neutral identity and protocol **4** / observation **2** / API **1** / handover **1**. All **72** signed deployed-file hashes and their exact closure matched the post-signing record; bundled consumer revision and all three file digests matched the pin.

These checks preceded the release commit: the local stage's compiled Core identity was its beta.3 parent `563e1662ad687249e419d483737c563f1246a32b`, not clean beta.4 tagged-source provenance. The exact beta.4 tag must be built again by official CI and its public assets independently verified. Local stage success does not pass any blocked real-handover gate below.

## Known limitations and recovery boundary

**Actual final packaged-consumer cold-load and reload, successful automatic handover with a fresh same-window/instance native receipt, original profile preservation through that handover, measured real SDK authority wall times, and 120 seconds of subsequent exchange remain unverified/blocked. External-PC recovery is not established.** Controlled Luau tests, readiness, a plugin listing, or a staged app do not replace these gates.

The available owned VM had **Tern 0.8.3 signed out** and standalone native **0.4.12**, with retained `awaiting_reconnect` state and settled forward delivery of the **old consumer**. That observation is not a corrected-consumer handover, signed-in recovery, or permission to fabricate approval/receipt evidence or force another installation path. The affected external PC requires its own actual evidence before recovery can be claimed.

This prerelease delivers a narrowly scoped existing correction for opt-in testing. It does not establish a supported automatic recovery outcome, extend migration authority to beta, or authorize bypassing validation, Stop, owner admission, fresh binding, or native receipt requirements.
