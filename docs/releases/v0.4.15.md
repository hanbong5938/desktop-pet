# Desktop Pet v0.4.15 release notes

## Recovery preflight and SDK validation children

The approved SSH recovery on the affected Mac reached preflight with the original Applications Pet already normally stopped. Two attempts refused transient native processes before any manual recovery operation or admission was created. Read-only investigation identified the unchanged Tern process spawning the genuine original `desktop-pet-update-coordinator`, which in turn spawned `desktop-pet pack validate` for the bundled default pack with private temporary config/state directories. These SDK-generated read-only validation children were classified as blocking clients; they were not evidence that the original Pet daemon had restarted.

The correction recognizes internal validation separately from compatible user CLI commands; it does not generally admit `pack` commands. The proof requires the exact bundled default-pack validation arguments and private scratch layout, a same-UID kernel parent relationship to the paired helper, and stable parent/child process and executable-vnode evidence. The paired helper is pinned against the fully validated signed deployment sidecar. Scratch ownership, permissions, creation timing and bounded contents are checked; its config/state directories must be empty. Both coordinated process scanning and stopped-profile discovery use this proof without counting the child as a user profile or client.

After a same-root exchange, authenticated immutable replacement evidence allows the retained scope's paths to change only when the moved app/helper still name the already pinned vnodes; it does not repin an arbitrary replacement. The exact authenticated pre-move launch namespace remains available for in-flight validators, alongside verified retained/current namespaces, not unrelated aliases. Internal validator ancestry checks remain PPID-strict. Ordinary control-peer identity continues to require UID, process incarnation, executable vnode and path, but does not treat a PPID change alone as an identity change.

Unknown processes and ordinary clients with foreign profiles remain blockers. Existing process authentication, executable identity, profile isolation and two-root installation guards remain intact. A blocker is not permission to ignore preflight or kill, pause or restart Tern or user processes.

## Preservation and release boundaries

The original profile, characters, settings and work remain the recovery source of truth. The original Applications bundle and verified config/state backup are retained; no private installation or successful recovery is claimed by these notes. Tern, its windows and terminal work must remain running without plugin reload, consumer replacement or native KV rewrite. Installation, a separately authorized Pet start and actual fresh Tern window connections are separate observations.

Published v0.4.14 and all existing tags, release assets and frozen release notes remain immutable. This correction uses a new v0.4.15 product version; independent legacy migration authority stays at 0.4.12. Legacy 0.3.16, contracts 0.1.0, protocol and qualified consumer pins are unchanged. Homebrew formulae are unchanged.

## Verification boundary

Source changes and release publication are not evidence of affected-machine recovery, private-owner readiness, preserved window continuity or a completed future update. Final local gates, exact tagged CI and any approved recovery observations must be reported separately. The package remains ad-hoc signed, not Developer ID signed or notarized.
