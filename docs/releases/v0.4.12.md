## Fixed: discovery and startup repeated full bundle validation

Full app-bundle validation (`validate_staged_app`) covers the deployed SHA-256 resource closure, strict/deep signatures, entitlements, system-only helper dependencies and native Rubelia `pack validate` rig preparation. That last step dominates its cost. Since Core v0.4.0, proving a standalone OS-home installation's owner also ran the full validation, and two callers repeated it for the same unchanged bundle:

- `desktop-pet-update-coordinator discover --json` and `installation inspect` validated the bundle once, then validated it again while proving the standalone owner. Tern's **Configure desktop pet connection** gives this command 10 seconds. On an affected loaded Mac, installed Core v0.4.8 took 10.2–25.4 s and failed with “native discovery/profile query timed out”. Owner resolution now reuses that same validation, but only when it covers the exact physical OS-home bundle being classified. The final image-identity recheck is unchanged.
- The `start`/`ensure`/`settings` launcher re-classified the owner at every startup admission: five times before spawning the daemon and once after readiness. On a loaded host, more than 90 s could pass without the daemon being spawned or its log changing. The launcher now classifies a verified owner once per launch, as the daemon already did. Every admission still rebuilds the launch context, re-hashes the running executable, re-reads migration startup authorization and re-checks the updater gates, reservations and user-stop generation. An unverified (Unknown) result is classified again at the next admission, so a transient validation failure never relaxes later installation-reservation checks.

Every verification still runs against the same bundle. Update Check, recovery, installed-candidate and migration proofs still validate independently.

## Observed evidence — not v0.4.12 qualification

The same code change was first measured on a Core v0.4.8-based release build of the update coordinator, against the same installed v0.4.8 bundle on the affected Mac (load average 17–35). Both builds produced byte-identical discovery records. The installed helper spawned two `pack validate` children and took a median 7.4 s wall time, with 9.4 s child CPU. The corrected build spawned one child and took a median 3.7 s wall time, with 4.7 s child CPU. Startup was not timed on the actual profile. These observations are not a v0.4.12 build, test or package result.
