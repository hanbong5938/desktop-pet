## Independent ownership and one native app

The core owns common runtime/UI, state, character packs, rig resources, settings, CLI, installation and native updates. Its Cargo workspace separates contracts, core, the composition-root app and update coordinator. Herdr and Tern own their concrete adapters/plugins in their own repositories; only the app composes adapters. Optional features allow zero-adapter builds without making host-specific app targets. Adapter/provider IDs remain opaque to core; source descriptors carry labels, locality and explicit prompt/worktree capabilities. A filesystem path or source-name prefix never grants mutation authority.

The Connection card selects Auto or a registered provider and displays actual coherent connections. Auto observes simultaneously, not fallback or priority. New profiles default to Auto; existing selections are preserved and legacy `both` becomes `auto` on read migration only. Provider retirement fences generations and stale snapshots, and uncertain offered prompts are not resent. Remote sources remain read-only; Tern does not offer worktree removal. Prompt acceptance remains separate from model completion.

## Installation and profile preservation

After actual release/formula publication, the public install command is `brew install hanbong5938/tap/desktop-pet`. Prebuilt and explicit source routes belong to the core checkout. Default installation is prebuilt-only; `--source` builds only that checkout and uses `dist/DesktopPet.app`, without claiming public availability. Standalone installs use the OS account home's `Applications/DesktopPet.app`.

Neutral profile precedence is explicit `--config-dir` / `--state-dir`, then `DESKTOP_PET_CONFIG_DIR` / `DESKTOP_PET_STATE_DIR`, then the atomic default-profile record, then `${XDG_CONFIG_HOME:-$HOME/.config}/desktop-pet` and `${XDG_STATE_HOME:-$HOME/.local/state}/desktop-pet`. Migration adopts existing config/state **in place**, preserving preferences, lifecycle, character/menu-bar stores, control locations and old updater evidence. Existing Tern/beta/custom profiles are not merged or moved; another neutral default is not overwritten. `profile show --json` is read-only, while explicit `profile adopt` sets the validated pair only. See [exact profile, locator and discovery rules](../development.md#profiles-and-installation-discovery).

The shared installation locator uses actual account-home `.local/share/desktop-pet/installation.json`. Discovery validates explicit path, locator, PATH, actual Brew prefix and standalone bundle in that order. Invalid explicit path/locator fails closed; locator text alone is not origin, signature or capability authority. Running image/profile mismatch is reported rather than silently launching another app.

## Thin host consumers

Herdr retains plugin ID/action IDs, host provenance, patched `client.attached` requirements and OMP outcome extension ownership. Its wrapper discovers/reuses a compatible core installation and forwards the selected profile and adapter-owned `--herdr-socket`; it does not own the common app build. Linking requires the core already installed/built, then linking the separate integration checkout. Plugin installation never patches Herdr.

Tern Connect/Configure validates and atomically saves the executable/config/state triple, using native read-only profile discovery for a new connection. It never installs, builds or auto-starts the native app. Configure preserves old profile paths when explicitly replacing a legacy executable; cancellation/failure keeps the old connection and no uncertain prompt is replayed. Host plugin updates/uninstall are independent: they never remove the shared app, profiles or characters. General native updates never reinstall host plugins.

## Updater and legacy A → B migration

Neutral native updates use only core release authority and verified standalone/Brew/core-source ownership. Automatic checks are read-only, beta opt-in remains off and installation needs explicit consent, Prepare, final visible prepared ACK and accepted reserved Stop. Installed is not applied. Unknown manager results are durable and must not be replayed; user Stop forbids automatic target or rollback restart.

Legacy users first perform **A: shipped 0.3.6 → actual bridge 0.3.7**, keeping matched protocol 3 / observation capability 1 and old image/origin proof. Only after A terminal/lease/reservation release may explicit **B: bridge → neutral 0.4.0** use the verified protocol-4 migration helper. B stages before Stop, keeps the same profile, verifies actual neutral image/version/readiness and retires only the authorized manager-owned old installation after commit. Readiness failure restores exact prior evidence/image; failed retirement is not migration completion. Tern requires user Configure and actual reconnect, not direct KV mutation.

Protocol-2 `0.3.5-beta.1` and older clients must settle old operations with their retained matching helper, stop the old daemon and use the **frozen pinned v0.3.6 prebuilt**, not the current evolving stable formula, before A → B. Older evidence is never reserialized into protocol 4. Both old/new account-global gates remain authoritative. Full procedure and Stop/Unknown/rollback/retirement limits: [migration guide](../migrations/desktop-pet.md).
