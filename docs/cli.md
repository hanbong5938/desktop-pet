## English

### Connection, identity, and operations

`desktop-pet` is the one host-neutral product executable. `--host auto|PROVIDER` selects a registered opaque provider; it is not a separate host app or fixed provider enumeration. New profiles default to Auto; legacy saved selections/read migration are described in the [profile contract](development.md#profiles-and-installation-discovery). Native profile precedence is explicit flags > neutral environment > default-profile record > neutral XDG defaults. The Herdr wrapper alone interprets its injected host profile and forwards explicit paths. Tern uses a validated executable/config/state triple and does not install or start a daemon.

`presentation`, `preferences`, `sessions`, `dialogue` and `worktree` use the running daemon’s private same-UID `<state-dir>/control.sock`. Select the same config/state pair for every command. `--herdr-socket ABS` is an **adapter-owned Herdr backend** option, never the control socket. With no registered Herdr adapter, core does not normalize/register a Herdr socket. Generic source locality/capabilities—not source prefixes, provider names or paths—authorize prompt/worktree operations. Remote is read-only; Tern has no worktree removal capability. No shell/raw-PTY fallback or uncertain delivery replay exists.

An `instance_id` is a daemon-lifetime nonce: obtain it from `presentation get` or other read results, and do not reuse it after restart. A session is the complete four-part key `(instance_id, source_id, generation, terminal_id)`; source/terminal alone or a GUI-selected first row is not an identity. Never blindly resend a mutation after a disconnect or timeout. An unknown/expired operation or a restarted daemon does **not** prove the original request never ran.

Default mutation wait is 15 seconds. `--no-wait` acknowledges accepted/pending work, not persistence or native application; an **already terminal failure** (including pack `failed`, `canceled`, `durability_unknown`, `committed_pending_apply`, or `unknown`) still exits nonzero, while a completed pack operation succeeds. `--wait SECONDS` is finite (presentation accepts 0–86400; the other domain families require >0–86400). Domain mutation/read and pack polling start their absolute wait deadline after their submission ACK; the partial-palette snapshot read likewise starts its own deadline after its read ACK, and must finish before any patch mutation is submitted. Each deadline covers sleeps and complete status RPCs, including trickled responses; a late terminal reply is not success. Domain **mutation** wait expiry prints `{"ok":false,"deadline_exceeded":true,"operation":…}` with the last known pending operation and a status-query error; domain **read** expiry instead returns a pending/status-query error without that JSON field. Presentation has `deadline_exceeded` in its mutation/status envelope. Early transport/protocol failure reports uncertainty instead of pretending the overall deadline elapsed. Expiry does not cancel, roll back, or resend. Read operation `state`, `committed`, `native_applied`, and result independently; a successful exit/ACK is not proof of agent answer, filesystem deletion, or AppKit application.

Domain mutations print `{"ok":boolean,"operation":{"instance_id":string,"operation_id":string,"kind":string,"state":string,"committed":boolean,"native_applied":boolean,"result":object|null,"error_code":string|null,"error":string|null}}`. `state` can be `accepted`, `pending`, `applied`, `agent_prompted`, `prompt_accepted`, `failed`, `unknown_delivery`, `superseded`, or `shutdown`. Herdr `agent_prompted` is a prompt-delivery ACK, not model completion; Tern `prompt_accepted` is terminal with `committed:false`, `native_applied:false`, `result.delivery:"accepted_may_be_queued"`: Tern accepted the ask, which may still be queued, and neither delivery to the model nor task completion is proved. Unknown delivery is never permission to resend. Domain status uses the same wrapper; failed terminal states return an error. A rejected request may not have an operation result. No-wait `ok:true` can describe a still-pending operation. Read-only session/dialogue/worktree commands below print their result object directly, not this wrapper. Values may be null before observation.

```text
desktop-pet preferences set [--language system|ko|en|zh-Hans|ja] [--theme warm_ivory|dusty_rose|moonlit_ink|custom] [--surface #RRGGBB] [--text #RRGGBB] [--muted #RRGGBB] [--border #RRGGBB] [--accent #RRGGBB] [--status-indicators on|off] [--menu-bar always|recovery_only] [--observation-host auto|PROVIDER] [--observation-local on|off] [--observation-remote on|off] [--machine ID ... | --clear-machines] [--expected-revision N] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet preferences status --instance ID --operation-id OPID
```

`set` requires at least one setting. Repeated `--machine` selects listed catalog IDs; `--clear-machines` conflicts with `--machine`. Unknown/disabled machine IDs fail with typed `error_code` (for example `unknown_machine`); inspect the catalog first. A partial color palette reads the saved palette, merges only supplied colors and binds the resulting write to its saved revision; a concurrent change fails instead of silently overwriting colors. Optional `--expected-revision` rejects concurrent settings changes (`revision_conflict`). `get` prints a domain wrapper whose `operation.result` contains `revision`, `desired`, `persisted`, `effective`, `pending_reasons`, `status_item_visible`, `effective_locale`, and adapter-owned `observation_catalog` when registered (`initialized`, `machines` with IDs, labels, enabled state and status). Typed preference snapshots include `language`, `bubble_appearance`, `show_status_indicators`, `menu_bar_mode`, `observation_host:"auto"|"PROVIDER"`, `observation_local`, `observation_remote`, and `observation_machines`. The current-source `--observation-host` (including `=VALUE`) accepts `auto` or a registered opaque provider ID; legacy `both`, empty/padded values and unregistered IDs are not new accepted selections. The wire patch is likewise strict; tolerant legacy reads are not new mutation values. Host/local/remote/machines are one save-first preference transaction and apply live without daemon restart; switching Tern hides Herdr-only controls but preserves saved scope choices. A failed save (`persist_failed`) leaves prior saved/runtime settings unchanged. CAS conflicts likewise do not apply. A later host target can make a pending operation `superseded`; a different target is not native proof for the earlier request. `committed:true` means saved, while `native_applied`/pending reasons describe the actual target's later UI state. These are not lifecycle `settings` flags.
CLI `--language` accepts **exactly** `system`, `ko`, `en`, `zh-Hans`, or `ja` (including `--language=VALUE`), rejecting typos, case changes, empty or padded values before profile/socket/storage access; loading an older disk preference with an unknown language still uses its tolerant fallback. `system` checks preferred OS languages in order: case-insensitive Japanese tags and simplified Chinese (`zh`, explicit Hans, or CN/SG region) are supported; explicitly traditional Chinese (Hant or TW/HK/MO unless explicitly Hans) is skipped in favor of the next supported language, otherwise English. CLI `--machine` replaces the **whole list** and requires every ID to be currently enabled. The GUI's trusted selection delta can retain or remove an already saved missing/disabled ID and add currently enabled IDs only; it does not loosen CLI validation. Quiet, visible color settings refresh only conflict/marked-text eligibility and labels, not field drafts, focus, selection, undo, or swatches; closing the panel stops that refresh.

The observation selector accepts Auto or a registered opaque provider, not a fixed Herdr/Tern enumeration. `--observation-local`, `--observation-remote`, `--machine`, and `--clear-machines` are Herdr-owned registered options; catalogs and opaque preference keys belong to the adapter. Generic core does not synthesize them when that adapter is absent.

### Sessions and agent prompts

```text
desktop-pet sessions list --instance ID [--filter all|idle|working|waiting|completed|unknown|offline] [--limit 1..128]
desktop-pet sessions show --instance ID --source N --generation N --terminal ID
desktop-pet sessions prompt --instance ID --source N --generation N --terminal ID (--text TEXT | --file PATH | --stdin) [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet sessions status --instance ID --operation-id OPID
```

`list` returns `{instance_id,revision,filter,total,matched,status_summary,rows,next_cursor:null}`. `--limit` defaults to 32 and accepts 1–128: it is **page size, not a total row limit**. The CLI collects all pages and validates instance/revision/filter/counts, never printing a mismatched partial collection as success. Rows and `show` include the four-part `key`, source label, locality, pane ID, availability, status, outcome, display status and metadata (title/agent/workspace or tab labels), not raw source sockets or working-directory/checkout/root paths. `show` can read a retained Offline row without making it promptable. `prompt` needs an eligible live source with local prompt capability; remote/read-only/stale/offline sessions are rejected. Exactly one of `--text`, `--file`, `--stdin` is required; the **client** reads UTF-8 file/stdin and sends text, not a daemon file-read request. Raw prompt input has a 512 KiB budget and normalized text has a 4096 UTF-8 byte limit; IME behavior is a GUI boundary, not a CLI completion guarantee.

Each daemon session-list page is bounded separately from ordinary 64 KiB domain results by **512 KiB for the entire encoded response**, including envelope, escaping, cursor and final LF. It returns the longest fitting row prefix up to the requested page size; if one row plus required cursor cannot fit, it reports a bounded error rather than truncating metadata or creating an empty continuation. The CLI's collected multi-page output may exceed 512 KiB.

Read-only example (use actual returned instance/row keys):

```sh
desktop-pet presentation get
desktop-pet sessions list --instance '<instance-from-get>' --filter all --limit 32
desktop-pet sessions show --instance '<row.key.instance_id>' --source '<row.key.source_id>' --generation '<row.key.generation>' --terminal '<row.key.terminal_id>'
```

### Dialogue

```text
desktop-pet dialogue list
desktop-pet dialogue get --target JSON --locale ko|en|zh-Hans|ja --slot KEY
desktop-pet dialogue set --target JSON --locale ko|en|zh-Hans|ja --slot KEY (--text TEXT | --file PATH | --stdin) [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue reset-entry --target JSON --locale ko|en|zh-Hans|ja --slot KEY [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue reset-character --target JSON [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue status --instance ID --operation-id OPID
```

`--locale` accepts exactly `ko`, `en`, `zh-Hans`, `ja`; case changes, empty/padded tokens fail. Locale overrides are independent and do not translate pack-owned metadata; missing authored translations retain the existing fallback.

`KEY` is `idle|running|waiting|unknown|head_tap|body_tap|pet|completion_observed`. `list` prints `{"targets":[{"identity":{"target":{"kind":"character|external_assets","id":"…"},"reference":{"id":"…","revision":N}|null,"generation":N},"name":"…","locales":[…],"slots":[…]}]}`. **Pass the entire serialized `identity` as opaque `--target JSON`**, not just its nested target ID; there is no separate `--ref` flag. The pack reference/revision and registry generation guard stale sources. `get` prints `{selection:{identity,locale,slot},authored:string|null,override:string|null,effective:string|null,baseline:{metadata_token:string,override_entry:string|null,target_overrides_token:string},active:boolean}`. `authored` is source text, `override` saved user text, `effective` resolved text (including host reaction fallback where applicable), and `active` means this target affects the current runtime character. Baseline JSON is the entire returned `baseline`, **not** `selection` or `target`. Omit it to perform a fresh read followed by one CAS mutation; no automatic mutation retry or blind overwrite. Entry set/reset compares source `metadata_token` plus that locale/slot's `override_entry`; an unrelated override in the same character does not conflict. Whole-character reset compares source metadata plus `target_overrides_token`, the hash of all that target's overrides; another character's override does not conflict. Source hash binds character identity, referenced pack revision/generation and authored locales; stale source/entry/target report typed `metadata_conflict`, `entry_conflict`, `target_conflict`, or `stale_target`. `reset-entry` clears only one override, `reset-character` clears that character's overrides, not authored pack dialogue. Empty or whitespace-only set clears that entry; nonblank text preserves raw spaces/newlines/tabs. Dialogue text is limited to **2048 UTF-8 bytes**; disallowed control characters fail. File/stdin are read on the client. A saved inactive target can report `committed:true,native_applied:false,active:false` and still be `applied`; do not equate `native_applied:false` with failed persistence. Active saves can remain pending native refresh. Save-first failure preserves the previous committed override/runtime view, with no ghost entry. The CLI neither discards a GUI editor draft/selection nor opens its modal feedback.
For `character(id)`, saved overrides are shared across that ID's authored revisions, while `--target` and CAS still pin the exact authored reference/generation. `active:true` means that shared target affects the currently selected character, **not** that the returned authored revision is selected: reading retained @1 while @2 is selected returns @1 authored/baseline but can still be active. Saving/resetting @1 can update @2's live bubble; `native_applied:true` requires the actual active renderer and the committed shared override to be accepted, not merely a successful save. Changes to the exact authored source, active renderer or same-target override can supersede pending native proof; metadata cache eviction or another target's override cannot. The GUI retains an exact `(target, reference)` selection, including an unavailable removed revision and its draft rather than silently switching revisions. Initial ready editor content hydrates even while focused if untouched; edits made before metadata (including raw whitespace and marked text) remain drafts, and deferred IME unmark gets a settling pass without overwriting later focus, selection, or undo. Cached metadata errors are not retried by polling: explicit editor reopen/selection or a fresh `dialogue get`/read can retry once; loading/successful reads coalesce.

Non-destructive example (replace both quoted JSON values with the exact `identity` and `baseline` from current `list`/`get`):

```sh
desktop-pet dialogue list
desktop-pet dialogue get --target '<identity JSON from dialogue list>' --locale en --slot idle
```

### Worktree removal

```text
desktop-pet worktree inspect --instance ID --source N --generation N --terminal ID
desktop-pet worktree remove --token TOKEN [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet worktree status --instance ID --operation-id OPID
```

`inspect` requires an **explicit four-part session key**, eligible live local linked checkout (not the main repo/root); it prints `{token,instance_id,expires_in_seconds:60,key:{instance_id,source_id,generation,terminal_id},workspace_id,pane_id,worktree:{repo_key,repo_root,checkout_path,branch:null,is_main:false,is_linked:true}}`. Unlike session listing, this intentionally discloses the destructive checkout path for review. `branch:null` means branch is not known from the upstream information, not that there is no branch. Token is locally fresh, expires after 60 seconds, one-use, frozen to the checked target and invalidated by restart/source change; inspect again after expiry. `remove` accepts **only** the token, not path/workspace ID/force. It consumes the token and rechecks identity; wrong generation or changed target fails. There is no `--force` override, Trash/undo, branch deletion, or guarantee that ignored files are preserved: upstream `force:false` rejects dirty tracked/untracked work but ignored files may still be lost. The branch remains. Review checkout contents, especially ignored files, and use only a disposable checkout you own. The backend removal has a CAS gap; the token/recheck cannot certify the filesystem against independent concurrent changes.
`expires_in_seconds:60` is the **initial lifetime when inspect issues the token**, not a refreshed countdown on cached operation status. Repeated status reads neither renew nor extend the token.

**Destructive example — do not execute until you own and have reviewed a disposable linked checkout.** The angle-bracket values are placeholders, not a first-row auto-selection or a runnable deletion script:

```sh
desktop-pet worktree inspect --instance '<owned-disposable-instance>' --source '<owned-disposable-source>' --generation '<owned-disposable-generation>' --terminal '<owned-disposable-terminal>'
# Review the exact worktree.checkout_path, repository root, workspace and ignored files first.
desktop-pet worktree remove --token '<fresh-token-from-reviewed-inspect>' --operation-id '<fresh-unique-operation-id>' --no-wait
desktop-pet worktree status --instance '<same-instance>' --operation-id '<same-operation-id>'
```

Removal `result` first has `{target:{key,workspace_id,pane_id,worktree},acknowledged:false,final_observed:false}`. Upstream ACK can make it `pending,committed:true,native_applied:false,acknowledged:true,final_observed:false`; that ACK does not prove checkout deletion. `applied` requires a later stamped coherent observation at the right source/generation with **both pane and session absent**; then `result.final_observed:true` and an `observation` are included. Even that is a watcher observation, **not filesystem certification**, and `native_applied` stays false. Upstream refusal, uncertain delivery, missing watcher, expiry, or daemon restart must not be treated as safe-to-resend or proof of disk state. Check the checkout independently if physical deletion matters.

### Pack commands and existing boundaries

`pack list`, `pack import --path PATH`, `pack validate --path PATH`, `pack preview --path PATH --output PATH [--phase idle|running|waiting|unknown] [--time-ms N] [--reaction head_tap|body_tap|pet|completion_observed] [--reaction-age-ms N] [--hit-overlay]`, `pack export ID [--revision N] --output PATH`, `pack select ID`, `pack update ID --path DIR`, `pack restore ID --revision N`, `pack remove ID`, and `pack status OPID` remain separate from dialogue editing. Mutation flags are `[--operation-id ID] [--expected-generation N] [--wait SECONDS | --no-wait]`; **select/restore IDs are positional** (no `--id`; select has no `--revision`, restore requires `--revision`). `--expected-generation` is a CAS guard. Pack output is its own `{operation_id,state,committed,ui_applied,generation,error}` operation, with states including `accepted`, `preparing`, `applying`, `completed`, `failed`, `canceled`, `durability_unknown`, `committed_pending_apply`, `unknown`; `ui_applied` differs from committed store state. With no daemon, default pack mutation executes synchronously in its own offline worker; explicit `--wait` or `--no-wait` requires a **running** daemon and does not secretly start one. An uncertain pack disconnect calls for `pack status OPID`, not a resend. Neither pack preparation/ACK nor a session prompt ACK certifies downstream agent completion.
With `--no-wait`, an initial pack reply already in a failed terminal state exits nonzero even without status polling; only accepted/preparing/applying is a pending ACK. Explicit waits use the post-ACK absolute deadline described above.

Herdr 소유자는 **`lifecycle.json`이 없을 때만** 첫 lifecycle 쓰기의 공유 profile writer 안에서 `exit_with_herdr:true`를 원자적으로 초기화합니다. 기존 파일에서 키가 없으면 false이며 명시적 false도 유지합니다. 기존 boolean `enabled`는 false까지 `auto_start`로 이전합니다. endpoint·시작 메타데이터·다른 소유자의 필드를 보존하며 `preferences.json`이 아닌 `lifecycle.json`에 저장합니다. 잘못된 JSON/값은 초기화하지 않고 오류이며 저장 실패는 기존 실행 정책을 유지합니다. Auto/어댑터 없는 앱은 Herdr 없이 살아 있고 아래 Herdr endpoint·단절 규칙은 Herdr 전용 선택에서만 적용합니다. `settings set KEY on|off`는 core `auto_start` 또는 등록 소유자 키만 허용하며 Herdr 어댑터가 없으면 `exit_with_herdr`는 core 키가 아닙니다.

Tern 플러그인은 별도 [Tern 저장소](https://github.com/hanbong5938/tern-desktop-pet)가 소유하며 일반 독립 사용에서는 앱을 다운로드·빌드·설치·자동 시작하지 않습니다. 새 연동을 별도로 설정할 때는 앱을 명시적으로 시작하고 실제 executable/config/state 세 값을 Configure에 저장한 뒤 Connect합니다. 아래 승인된 migration은 별도 경로로, bundled consumer의 SDK 저장·실제 같은 창의 fresh binding을 자동 수행하며 수동 Configure 절차를 추가하지 않습니다. 기존 별도 프로필은 합치거나 지우지 않습니다. Herdr 플러그인은 별도 [Herdr 연동](https://github.com/hanbong5938/herdr-desktop-pet)이 소유합니다. 정상 앱 업데이트는 플러그인을 재설치하지 않고 플러그인 제거는 공용 앱·프로필·캐릭터를 남깁니다.

`--host auto|PROVIDER`는 Auto 또는 등록된 불투명 제공자 ID를 선택합니다. 앱 변형이나 고정 Herdr/Tern 열거가 아닙니다. 시작 선택 우선순위는 명시적 CLI > `DESKTOP_PET_OBSERVATION_MODE` > 저장된 `observation.host` > 새 프로필 Auto입니다. 기존 저장 선택은 유지하며 host-less 레거시 설정은 Herdr, 이전 `both`는 읽기 이전에서만 `auto`로 정규화합니다. 새 변경 값으로 `both`를 받지 않습니다. 실행 중 변경은 Connection 또는 `preferences set --observation-host auto|PROVIDER`로 저장 후 적용합니다. Auto는 등록된 제공자를 동시에 관찰하며 fallback·세션 이름/경로 중복 제거가 아닙니다. 작업 권한은 이름 접두사/경로가 아닌 출처 locality/capability로 결정합니다. 원격은 읽기 전용, Tern은 worktree 삭제 권한이 없습니다. Auto/어댑터 없는 앱은 호스트 단절에도 살아 있고 가짜 Herdr socket을 등록하지 않습니다.

```sh
./dist/DesktopPet.app/Contents/MacOS/desktop-pet --host tern start
./dist/DesktopPet.app/Contents/MacOS/desktop-pet status
```

`tern-exchange --config-dir ABS --state-dir ABS`는 등록된 Tern 어댑터 소유의 동일 UID 전용 내부 일회 UTF-8 JSON stdin/stdout 확장이지 공개 API/시작 명령이 아닙니다. 요청은 256 KiB(선택 framing LF/CRLF 제외), 전체 응답은 LF 포함 512 KiB입니다. 첫 바인딩에는 명령을 제시하지 않으며 이후 ask는 한 번만 제시하고 불확실한 전달·제공자/바인딩 변경 뒤 다시 보내지 않습니다. 창 출처는 5초 뒤 만료하고 모든 제공자가 64개 출처 한도를 공유합니다. 로컬 창/그룹 호스트 목록은 어댑터가 승인한 locality를 유지하고 로컬처럼 보이는 경로로 원격 권한을 올리지 않습니다. 정확한 현재 wire schema 및 연결 저장·복구는 Tern 저장소가 소유합니다.

`--herdr-socket ABS`와 backend endpoint 정규화/등록은 Herdr 어댑터 소유입니다. 어댑터가 없으면 core는 Herdr socket을 해석하거나 가짜 등록하지 않습니다. backend 경로는 실제 연결 증거가 아니며 제어 socket은 항상 선택 state의 `control.sock`입니다. Tern의 정규 `connection={version=1,executable,config_dir,state_dir}`는 전체 검증 뒤 한 번 KV 저장하고 profile/incarnation을 전환합니다. 취소·실패는 이전 triple을 보존하고 지연 콜백은 전환을 넘지 못합니다. 잘못된 정규 값은 이전 값으로 fallback하지 않습니다.

`status.host_connections`는 불투명 provider ID별 실제 연결되고 일관된 출처 수의 map입니다. 등록된 Herdr/Tern은 `herdr`/`tern` 키 의미를 유지합니다. 설치 여부·활성 스위치·세션 수가 아니며 실제 출처가 `data_connected`를 결정합니다. live 변경은 먼저 저장하고 비활성 출처/generation을 폐기합니다. 늦은 목록은 되살리지 못하고 오래된 세션 키는 실패합니다. 다시 전환해도 제시/불명확한 prompt를 재전송하거나 다른 제공자로 보내지 않습니다.

프로필 우선순위는 **명시적 `--config-dir`/`--state-dir` > `DESKTOP_PET_CONFIG_DIR`/`DESKTOP_PET_STATE_DIR` > default-profile record > 중립 XDG 기본값**입니다. 기본값은 `${XDG_CONFIG_HOME:-$HOME/.config}/desktop-pet`, `${XDG_STATE_HOME:-$HOME/.local/state}/desktop-pet`입니다. core는 `HERDR_PLUGIN_*`를 암묵적 기본값으로 해석하지 않고 Herdr wrapper만 주입 경로를 명시적 native 인자로 전달합니다. `profile show --json`은 읽기 전용이며 daemon/디렉터리를 만들지 않습니다. `profile adopt --config-dir ABS --state-dir ABS`는 검증된 비활성 소유 pair를 원자적으로 선택할 뿐 데이터 이동/병합이 아닙니다. active 예약/update, 다른 live daemon, invalid/symlink/nonowned 경로는 변경 전에 실패합니다. 공유 locator·실행 파일 검증은 [프로필/탐색 계약](development.md#profiles-and-installation-discovery)을 따릅니다.

`instance_id`는 데몬 생존 기간의 nonce입니다. `presentation get` 등의 읽기 결과에서 얻고 재시작 후 재사용하지 마십시오. 세션 키는 `(instance_id, source_id, generation, terminal_id)` **네 요소 전체**입니다. 소스·터미널만으로, 또는 GUI의 첫 행 선택으로 대상을 추측하지 마십시오. 변경 작업의 `operation_id`는 생략하면 생성됩니다. ACK 손실에 대비하려면 **전송 전에** 고유 `--operation-id ID`를 지정하십시오. 연결 끊김/시간 초과 후 재전송하지 말고 같은 계열의 상태를 조회하십시오. `presentation status OPID --instance ID`와 `pack status OPID`의 OPID는 위치 인자입니다. `preferences|sessions|dialogue|worktree status --instance ID --operation-id OPID`는 각각 자기 계열 작업만 조회합니다. 재시작·만료·unknown 상태가 원래 변경이 실행되지 않았다는 증거는 아닙니다.

기본 대기 시간은 15초입니다. `--no-wait`의 수락/대기 ACK는 저장 또는 네이티브 적용을 뜻하지 않습니다. **이미 종료된 실패**(팩의 `failed`, `canceled`, `durability_unknown`, `committed_pending_apply`, `unknown` 포함)는 `--no-wait`에도 종료 코드가 0이 아니며 팩 `completed`는 성공입니다. `--wait SECONDS`는 유한합니다(presentation 0–86400초, 나머지 도메인 >0–86400초). 도메인 변경·읽기와 팩 폴링은 각 제출 ACK 뒤 절대 대기 기한을 시작합니다. 변경 전 부분 색상 스냅샷 읽기도 읽기 ACK 뒤 별도 기한을 시작하며 그 안에 끝나지 않으면 변경을 제출하지 않습니다. 각 기한은 sleep과 전체 status RPC(조각 응답 포함)에 적용되며 늦게 도착한 종료 결과를 성공으로 보고하지 않습니다. 도메인 **변경** 기한 초과는 마지막 확인된 pending 작업을 담은 `{"ok":false,"deadline_exceeded":true,"operation":…}`와 status 조회 안내 오류를 출력합니다. 도메인 **읽기** 기한 초과는 이 JSON 필드 없이 pending/status 조회 안내 오류를 반환합니다. presentation의 변경/status 봉투에는 `deadline_exceeded`가 있습니다. 기한 전에 발생한 전송/프로토콜 실패는 기한 초과가 아니라 전달 불명으로 보고합니다. 시간 초과는 취소·롤백·재전송하지 않습니다. `state`, `committed`, `native_applied`, `result`를 별도로 해석하십시오. ACK 또는 성공 종료만으로 에이전트 답변, 실제 파일 삭제, AppKit 적용이 인증되지는 않습니다.

도메인 변경 출력은 `{"ok":boolean,"operation":{"instance_id":string,"operation_id":string,"kind":string,"state":string,"committed":boolean,"native_applied":boolean,"result":object|null,"error_code":string|null,"error":string|null}}`입니다. `state`는 `accepted`, `pending`, `applied`, `agent_prompted`, `prompt_accepted`, `failed`, `unknown_delivery`, `superseded`, `shutdown` 중 하나입니다. Herdr의 `agent_prompted`는 프롬프트 전달 ACK이지 모델 완료가 아닙니다. Tern의 종료 상태 `prompt_accepted`는 `committed:false`, `native_applied:false`, `result.delivery:"accepted_may_be_queued"`이며 Tern이 ask를 수락했으나 대기열에 있을 수 있어 모델 전달/작업 완료를 입증하지 않습니다. 불명확한 전달을 재전송 허가로 보지 마세요. 계열별 status도 같은 래퍼를 반환하고 실패 종료 상태는 오류를 반환합니다. 거절된 요청에는 작업 객체가 없을 수 있습니다. `--no-wait`의 `ok:true`여도 아직 pending일 수 있습니다. 세션/대화/워크트리 읽기는 래퍼가 아닌 결과 객체를 직접 출력합니다. 관측 전 필드는 null일 수 있습니다.

공개 전 소스의 실행 근거는 일반적인 완료 보장보다 좁지만 주입한 수락 결과에만 국한되지는 않습니다. 이미 실행 중인 현재 사용자의 Tern 창에서 전용 검증 프로필·플러그인 kv 및 Tern CLI로 만든 본인 소유 일회용 OMP 탭을 사용했으며 실제 플러그인이 전용 소켓으로 에이전트 목록을 교환했습니다. 소유 pane의 네이티브 `sessions prompt`는 실제 `agents:ask` 수락 후 `prompt_accepted`, `committed:false`, `delivery:"accepted_may_be_queued"`를 반환했습니다. 같은 pane의 Tern `agents:transcript`에는 `Reply with exactly TERN_PET_SMOKE_OK. Do not use tools or modify any files.`에 이어 assistant `TERN_PET_SMOKE_OK`가 기록되었고 idle 상태와 일치하는 `last_message`도 관측했습니다. 이 transcript는 해당 답변의 근거이지 권위 있는 완료 이벤트나 성공 애니메이션의 근거가 아니며 idle만으로 완료를 인증할 수 없습니다. 도우미 주도 전체 업데이트 거래를 실행하거나 로컬 플러그인/소스 CLI를 기존 공개 아카이브에 게시하지 않았습니다.

공개 전 수정 근거는 이전 의미 있는 smoke와 별개입니다. 네이티브 674개 통과·1개 무시와 실제 AppKit composer, 코디네이터 70개(라이브러리 49·바이너리 21), TypeScript/Bun 58개, arm64 릴리스/패키지 및 ad-hoc strict/deep 서명을 확인했습니다. 실제 Tern 0.6.1의 생산 `window.luau`를 제어된 SDK로 실행한 **44/44개**이며 독립 모델이나 일반 모델 전달 보장은 아닙니다. 50 ms 수정은 `tern.sleep(0):next` microtask 네 번으로 tabs·sessions·agents를 각각 읽고 마지막에 hosts+panes와 순수 검증을 수행합니다. 콜백당 목록 API는 최대 두 개(API당 12 ms에서 24 ms)입니다. busy/프로필/incarnation/단계 fence가 비동기 목록 전체를 보호하고 최종 중요 local/pane/agent 검사는 신선한 일관된 context를 씁니다. accepted/failed 보고는 신선한 전체 스냅샷 교환을 즉시 시작하고 기존 1200 ms 타이머를 기다리지 않습니다. 캐시·ask 재시도·프로토콜 변경·네이티브 5초 영수증 기한 증가는 없습니다. 타이머 지터는 997 ms까지 측정했지만 개별 SDK 호출/OS 선점은 모델 밖이며 일반 프로세스 오버헤드는 측정하지 않았습니다. 요청 JSON은 선택적 framing LF/CRLF 제외 정확히 256 KiB, 응답은 LF 포함 512 KiB입니다. 이전 허용된 411918바이트 CLI 요청은 이제 IPC 전에 거절됩니다. 한도 때문에 거절된 건강한 Herdr는 연결을 유지하고 정상 다음 일관된 스냅샷에서 허용하며 첫 기준선은 과거 완료나 별도 재시도 스레드/backoff를 만들지 않습니다. 서명된 현재 Tern·legacy protocol-3 도우미는 부모 없는 사전 검사·정확한 Original NoSpawn 복구, `Failed`, `installed:false`, `applied:false`, 예약 해제·원본 유지를 입증했습니다. capability 없는 legacy `{"protocol":3}`는 키 없는 기본 Herdr를 허용하지만 명시적 Herdr 등 모드 키가 있으면 capability 1이 필수입니다. **Completed GUI Apply/신선한 Candidate 인계는 주장하지 않습니다**(`AXIsProcessTrusted=false`). 최종 네 microtask 생산 코드는 실제 `agents:ask`를 기한 내 수락했고(`prompt_accepted`, `committed:false`, `native_applied:false`, `accepted_may_be_queued`) 소유 assistant는 정확히 `TERN_MICROTASK_SMOKE_OK`로 답했습니다. 해당 답변의 증거이지 일반 완료 보장은 아닙니다. 15초 연결 표본 다섯 번과 정규 A→B 전환 완료(6.25초 뒤 기존 A 끊김·새 B 연결)를 관측했지만 무기한 신뢰성 보장은 아닙니다. 이전 `TERN_REPAIR_SMOKE_OK`와 transcript로 조정된 `TERN_COOPERATIVE_SMOKE_OK`는 해당 답변만 입증하고 불명 전달은 맹목 재전송하지 않았습니다. [개발 근거](development.ko.md)를 참고하세요. 그 검증 당시 소스/플러그인은 미게시였으며 현재 v0.3.6과 공개 플러그인은 게시됐습니다.

### 앱 업데이트 상태와 복구

```text
desktop-pet update-capabilities
desktop-pet update-status [OPID] --state-dir PATH
```

데몬 없이 가능한 읽기 전용 명령입니다. 현재 neutral `update-capabilities`는 `{"protocol":4,"observation_mode":2,"integration_api":1}`입니다. 이전 v0.3.6 및 bridge envelope는 protocol 3 / capability 1로 분리됩니다. 업데이트 ID는 소문자 16진수 32자리이며 도메인 작업 ID와 다릅니다. ID 생략 시 진행 예약이 마지막 결과보다 우선합니다. neutral 계획/저널은 version 4이고 `execution_fence` (`no_spawn`, `manager_intent`, `manager_exited`)를 유지합니다. `no_spawn`과 manager 흔적 부재가 미실행을 입증하며 실행 전 저장된 `manager_intent`는 PID/종료 정보가 없어도 불명이지 재시도 허가가 아닙니다. `manager_exited`는 종료·출력 배출 증거가 필요합니다. phase/fence/installed/applied는 별개이고 오프라인 status는 저장 증거이지 현재 이미지·서명/준비 인증이 아닙니다.

중립 updater는 정확한 선택 모드, image/origin, config/state, 외부 assets를 재시작/복구까지 고정하며 임의 상속 host 환경으로 바꾸지 않습니다. 앱·도우미는 protocol 4 / observation capability 2 / integration API 1의 일치하는 envelope와 정확한 준비 선택을 검증해야 합니다. 이전 protocol-3 context의 기본 Herdr/구 capability 규칙은 역사적 matching helper의 책임이지 v4 fallback이 아닙니다. 불명/잘못된/미래 capability는 추측하지 않고 거절합니다.

실시간 호스트 변경이 성공하면 updater의 캐시 context를 갱신하고 이전 진행 중 확인 결과·후보·동의를 무효화합니다. 새 모드로 다시 확인하고 새 동의를 얻으세요. 마지막 작업 이력이나 이미 소유한 도우미 계획·저널·lease·예약은 버리지 않습니다. 실제 준비 중에는 충돌하는 설정 변경을 `update_preparing`으로 막아 소유권과 고정 작업 context를 인계/복구까지 유지합니다.

설정 카드의 **현재 읽기 전용 확인·진행 상태**와 보존된 **마지막 업데이트 작업 결과**는 별개입니다. 자동 확인(기본 켜짐)과 **베타 업데이트 받기**(기본 꺼짐)는 독립적이며, 안정판 전용 `last_update_check`와 베타 포함 `last_beta_update_check`도 별도입니다. 스위치 변경은 설치·재시작하지 않으며 자동·수동 확인은 Brew 메타데이터를 갱신하거나 Git을 변경하지 않습니다. 안정판만 선택하면 안정판만, 베타를 받으면 안정판·베타 중 정확한 SemVer 최고 버전을 선택합니다. 동일 기본 버전의 최종 안정판이 베타보다 우선하고 베타 해제만으로 다운그레이드하지 않습니다. 이후 확인으로 현재 상태가 바뀌어도 이전 `Failed`·`Unknown`·`Completed` 이력이 사라지지 않습니다. 기본 화면의 실행 버전·간결한 출처·상태 안내는 선택한 한국어·영어·중국어 간체·일본어 UI를 따릅니다. 처음 접힌 진단 정보를 펼치면 전체 경로·해시·출처/확인/작업 ID·후보·저널·오류 원문을 선택·복사할 수 있으며 원본 기술 값은 번역하지 않습니다. 오프라인 `update-status`는 저장된 증거 조회이지 현재 준비 상태 검사 도구가 아닙니다. `installed:true`만으로 교체 인스턴스의 실행·준비 완료를 보장하지 않으며 `applied:true`도 공개 최신판이나 전체 채널 전환을 뜻하지 않습니다. 확인은 lifecycle·설치·실행 이미지·선택 프로필을 바꾸지 않지만 성공 확인은 `preferences.json`의 정책별 timestamp 캐시(`last_update_check` / `last_beta_update_check`)를 쓸 수 있으므로 바이트 단위 읽기 전용은 아닙니다.

남은 private 도우미의 코드 서명을 검증한 뒤 그 도우미의 `status --state-dir PATH --operation-id OPID`로 현재 도우미·관리자·후보 증거를 확인하세요. 명시적 `recover --state-dir PATH --operation-id OPID [--start]`는 작업별 lease를 유지하며 기존 도우미가 lease를 점유한 동안 복구 요청을 거절합니다. 설치를 반복하지 않고 조정합니다. `no_spawn`과 관리자 흔적 부재, 정확한 기존 PID·인스턴스·이미지·소스·프로필의 준비 완료가 입증되면 예약을 해제하면서 `Failed`, `installed:false`, `applied:false`로 기록할 수 있습니다. 변경 없는 원본이 종료된 경우 시작하지 않고 조정할 수도 있습니다. 새로 준비된 원본 인스턴스는 원본 종료 검사보다 먼저 확인하며 업그레이드가 아니라 `Failed`입니다. 검증된 설치 후보 시작이나 검증된 원본 복원은 명시적 `--start`에서만 허용하며 설치와 적용은 다릅니다. 일부 예약 표식 해제는 반복해도 안전하게 조정합니다. 해제가 불완전/불명확하거나 관리자·그룹·출력·증거를 입증할 수 없거나 다른 프로필·동일 설치 범위의 실행 사용자·더 최신 사용자 Stop이 있으면 안전을 우선합니다. `Unknown`은 예약을 유지하고 설치를 재실행하지 않습니다. 표식을 삭제하거나 원래 설치를 맹목적으로 재시도하지 마세요. 안전하게 정리된 실패 뒤 새 확인과 사용자 동의는 **별개의 새 작업**이지 이전 설치의 재생이 아닙니다. `run`은 앱의 서명된 도우미 인계용이며 범용 설치 CLI가 아닙니다.

현재 도우미의 `ui_recovery_contract:1`은 `recover-ui --state-dir ABS --operation-id ID [--start]`를 뜻합니다. 기본 동작은 설치 없는 조정이며 시작은 새로 검증한 이미지에 대한 별도 네이티브 동의가 필요합니다. 중립 도우미의 `ui_recovery_legacy_contract:1`은 `recover-legacy-ui --state-dir ABS --operation-id ID`이며 `--start`를 받지 않습니다. 이 경로는 명시적 동의 뒤 캡처한 Pet만 종료하고, 보존된 정확한 원래 도우미가 자신의 근거를 해석·정리하도록 조정합니다. 구 프로토콜 근거를 새 도우미로 재해석하거나 설치를 반복하지 않습니다. 정리 후 수동 시작은 별도 네이티브 동의가 필요하며 사용자 Stop을 자동 시작 권한으로 바꾸지 않습니다. 일반 사용자는 설정의 복구 버튼으로 실행합니다.

후보 복구에는 내구성 있게 고정된 정확한 이미지와 선택된 설치 출처가 모두 필요합니다. targetless image-only/origin-only 기록으로 현재 디스크에서 빠진 pin을 보충하거나 후보를 시작하지 않습니다. 완전한 쌍의 호환되는 일부 예약 표식은 manager 재실행 없이 복구합니다. 호환되지 않는 후보 출처가 선택되지 않았고 원본이 독립적으로 정확히 검증된 경우에만 별도의 내구성 있는 실패 목적으로 원본을 복원하며 과거 이미지는 지우지 않습니다. 같은 이미지의 로컬 재빌드도 Candidate 목적과 새 준비 증거를 유지합니다. 사용자 Stop은 새 시작 token을 허용하지 않지만 완전히 입증된 안전한 종료 작업의 조정·예약 해제는 가능합니다. 설치 변경·pin 충돌·불명확한 manager 실행은 Unknown으로 남습니다.

도우미는 한국어·영어·중국어 간체·일본어 단계 문구와 불확정 진행 표시를 제공하고 **완료 처리(Finalizing)**를 거쳐 **완료(Completed)**로 전환합니다. 성공 창은 새 인스턴스의 준비, 내구성 있는 최종 결과 기록, 예약 해제 성공 뒤에만 자동으로 닫힙니다. 실패·불명 상태에는 창과 펼쳐서 선택·복사할 수 있는 원본 진단이 남으며 원본 기술 값은 번역하지 않습니다. 도우미 창 닫기는 표시만 숨기며 작업 취소나 증거 삭제가 아닙니다. 변경 없는 원본을 그대로 두거나 복원한 결과는 **업그레이드가 아닌 실패한 업데이트**이므로 설치를 반복하지 마세요. 복구는 설치 재시도·롤백·재시작을 암묵적으로 하지 않습니다. 기존 입증 규칙에 따라 명시적이고 검증된 `recover --start`만 후보 또는 원본을 시작할 수 있으며 사용자 Stop이 우선합니다. 정리된 실패 뒤 새 확인·새 동의는 과거 작업 재실행이 아닌 별도 작업입니다.

기존 작업의 `run`은 실행 fence나 lifecycle 증거를 바꾸기 전에 이미 있는 journal을 거절합니다. 설치 재실행이 아닌 `recover`를 사용하세요. 외부 설치가 검증된 후보도 명시적 `recover --start`나 우선하는 사용자 Stop 전까지 `Failed`, `installed:true`, `applied:false`와 예약이 남을 수 있습니다. 수락된 Stop 응답을 읽지 않았다는 사실만으로 서버의 응답 쓰기 실패를 입증할 수는 없습니다.

현재 소스의 neutral `SourceRebuild`는 staging manager 성공과 실제 설치 commit을 분리합니다. private `<operation>.replacement.json`의 stage-only 기록은 설치 증거가 아닙니다. 원자 bundle 교체 뒤 실제 installed image를 기록한 완료 receipt와 최종 `manager_exited` fence가 모두 있어야 하며, 바이트가 같은 재현 빌드도 예외가 아닙니다. receipt 부재/stage-only에서는 독립 검증한 변경 없는 원본만 `Failed`, `installed:false`, `applied:false`로 복원할 수 있습니다. commit intent, 안전하지 않거나 다른 작업/실제 이미지와 모순되는 receipt, 완료 receipt 없는 candidate pin은 `Unknown`과 예약을 유지합니다. 완료 receipt도 staging manager의 성공·출력 drain·프로세스 quiescence 증거를 대신하지 못합니다. 조회는 증거를 쓰지 않고, 복구는 staging/commit을 재실행하거나 빠진 receipt/fence를 추정하지 않으며 사용자 Stop은 새 시작을 금지합니다.

보존한 `legacy-0.3.12` ingress는 검증된 로컬 Source checkout도 prebuilt-only입니다. 변경 없는 bridge는 rebuild plan 없이 `Current`이고 Cargo/native 파일 추가로 rebuild가 활성화되지 않습니다. 실제 다른 검증된 설치 이미지는 `ApplyInstalled`로 적용할 수 있습니다. 과거 `local_rebuild`는 증거로 decode하되 Stop 전에 `legacy bridge ingress does not support source rebuilding`로 거부하며, 자격을 갖춘 경우 별도 승인한 Desktop Pet migration을 사용합니다.

기존 protocol-1/2/3 계획·저널·예약은 원래 바이트 그대로 차단·보존하며 v4로 변환·기본값 대입·별칭·삭제하지 않습니다. **matching-protocol의 보존된 서명 helper**로만 조회·복구하세요. neutral 설치기는 일치하는 protocol 4 / capability 2 / integration API 1 쌍만 허용합니다. release authority는 `hanbong5938/desktop-pet`이며 standalone/Brew/core-source 소유자를 구분합니다. 정상 native update는 Herdr plugin manager를 사용하지 않습니다. Brew는 실제 manager/prefix와 전체 formula Cellar subtree를 fence하고 prefix 전체를 설치 경계로 보지 않으며 다른 formula를 몰래 uninstall하지 않습니다. source rebuild는 현재 파일/Git 내용을 보존합니다. 과거 A→B는 별도 동의와 검증된 v4 `migrate-legacy --plan ABS`를 사용했으며 수정된 일반 경로는 아래처럼 진짜 원래 승인을 위임합니다([이전 안내](migrations/desktop-pet.md)). `updates-v4/`/실제 계정 home `.desktop-pet-updates`와 기존 `updates/`/`.herdr-updates`는 공존하고 lock 순서는 old global → new global → 정렬 roots이며 legacy stop-generation도 검사합니다. 사용자 Stop은 재시작·rollback start보다 우선합니다.

### Tern을 유지하는 standalone 설치 transaction (현재 소스 계약)

고정 prebuilt 설치기의 경로는 검증된 helper의 `install-coordinated --request ABS`입니다. 일반 Standalone 설치·업데이트와 reuse는 private 정식 소유자만 허용하며 Applications를 조용히 재등록하지 않습니다. beta.7 복구는 터미널이 아닌 앱 업데이트에서 시작하고 구 helper가 완전히 정산한 뒤 별도 native 동의로 같은 정식 버전을 이관합니다. 앱의 자동 `install-relocate --request ABS`와 명시적 재시도 `install-relocate-manual --request ABS`는 strict v1 `{version,context,parent}`만 받으며 임의 경로·새 프로필을 승인하지 않습니다. 취소·승인창 실패·다른 active profile 충돌은 Stop 전에 종료합니다. **Pet만 재시작하고 Tern·창·터미널·작업은 유지**하며 미저장 Pet 편집은 먼저 저장하세요. 실제 GUI 검증·공개 성공을 뜻하지 않습니다.

`installed`는 디스크 교체, `applied`는 새 인스턴스·동일 프로필/관찰/assets·UI/control 준비 확인입니다. 원래 stopped였으면 `installed_stopped` / `restart:"not_requested"`로 끝나며 시작하지 않습니다. 미확정/시작 실패는 원본 보존 성공으로 표시하지 않습니다. 보고된 operation ID/state-dir 및 보존된 서명 helper로 `install-status --state-dir ABS --operation-id ID`, `install-recover --state-dir ABS --operation-id ID`를 사용하세요. status의 exit 0은 관찰 성공이지 설치 성공이 아닙니다. 일반 updater의 `recover --start`와 혼용하지 않습니다. Stop ACK 유실·미전이 index·추가 사용자 Stop는 복구 동의로 재시작 권한이 되지 않습니다. 디스크·실행 종료가 확인된 release-only 복구는 재시작 없이 예약만 해제할 수 있습니다. old bundle과 **원래 sidecar**는 private storage에 보존하며 자동 삭제하지 않습니다. 진행/불명 작업의 증거·도우미·stage·표식을 임의 삭제하지 마세요.

### 수정된 후속 bridge 자동 업데이트 (v0.3.15 → Core v0.4.11; 소스 계약이며 배포 증거 아님)

후속 bridge는 구형 별도 A/B 동의를 대체합니다. 한 번의 원래 승인이 정확한 Core 릴리스·기존 config/state·관찰 선택·native 재시작·설정된 Tern consumer 전달·옛 소유자 retirement를 승인합니다. 실제 설치 v0.3.10/v0.3.11을 포함한 허용 stable protocol-3 source v0.3.9–v0.3.14의 보존된 진짜 plan/result·matching signed original helper·해제된 lease·확정 성공/quiescent manager 결과가 정확한 현재 v0.3.15 candidate/image·설치 root/owner·원래 profile·불변 Stop fence와 일치해야 합니다. 과거 Completed v0.3.11 candidate·Unknown·prerelease/미지 source·protocol 2·hash 변경·무관 profile·사용자 Stop은 fallback 권한이 아닙니다. v0.3.6 및 동결 protocol-2/beta entry는 별도 호환 경로입니다. 옛 기록을 재실행하거나 바꾸지 않습니다.

이미 실행 중인 후속 bridge의 명시적으로 승인된 비대화형 경로는 `herdr-desktop-pet update --yes --config-dir /원래/절대/config --state-dir /원래/절대/state`입니다. 두 경로가 필요하며 실제 daemon의 시작 시점 소유자·환경을 private control socket으로 검증합니다. `--yes`가 원래 업데이트 승인이고 불명 작업 우회나 가짜 VisibleApproved가 아닙니다. 정상 경로에 추가 이전 창·Configure·재연결 확인 파일·수동 Resume는 없습니다. 이미 배포된 옛 실행 파일 자체의 대화상자는 소스 변경으로 소급 제거할 수 없습니다.

각 승인 profile의 Prepare/Stop → 정확한 target NativeReady·durable Commit → `integrating` → bundled consumer 전달·로드 → SDK optimistic identity guard와 atomic canonical save → 실제 같은 Tern 창의 fresh binding → 자동 native handover receipt → 승인된 공유 소유자 retirement → `complete` 순서입니다. **실제 binding·receipt가 retirement보다 먼저**이며 SDK guard는 진정한 cross-VM transactional CAS가 아닙니다. 설치 성공·reload 요청·ACK는 재연결 증거가 아닙니다. Commit 후 전달·load·SDK cutover·binding 실패는 “앱 Commit됨; 연동 불가; retirement 대기”이며 전체 완료가 아닙니다. 옛 설치/alias와 증거를 유지하되 중지된 옛 실행 파일 보존을 연결 복구로 주장하지 않습니다. linked/read-only 설치·Tern 부재·계정/오프라인 reload 실패·실제 adapter 오류를 숨기지 않습니다. 불명 manager/delivery intent는 replay하지 않으며 사용자 Stop은 자동 시작·전달·rollback restart를 막습니다. 실제 othermachine의 Commit 후 낡은 저장 경로 `/opt/homebrew/bin/herdr-desktop-pet`는 manager 재실행 사유가 아닙니다. same-image 및 적격 successor `AwaitingReconnect` 복구는 검증된 현재 image/profile·정확한 owner upgrade 또는 installation/deployment 증거·서명된 옛 target stage/keg에 묶인 별도 `OPID.migration-settlement.json` 및 새 repair/handover receipt로만 앞으로 조정합니다. 옛 plan/journal은 byte-identical로 보존하고 실패·Unknown·사용자 Stop을 성공으로 바꾸지 않습니다. 수동 Ack/Configure/Resume은 일반 복구 단계가 아닙니다.

기본 record가 없거나 같은 원래 config/state 쌍을 가리킬 때만 그 쌍을 기본으로 사용하며 다른 기본 선택은 덮어쓰지 않습니다. 여러 profile이면 각자의 config/state·환경·관찰 선택·Stop generation과 PID/instance/image/NativeReady/Commit을 `target_profiles`에 유지합니다. 모든 필요한 연동 binding·receipt 전에는 공유 소유자를 retirement하지 않습니다. primary 증거가 secondary 성공을 대신하지 않으며 일부 profile 실패 때문에 이미 Commit한 target을 rollback하지 않습니다. 무관한 neutral Brew profile은 읽기 전용으로 검증된 이전 keg에 남길 수 있지만 source/standalone 교체는 비활성 target root가 필요합니다. 동결된 옛 Stop API에는 draft/Unknown 보존을 인증할 Prepare 계약이 없기 때문입니다.

Tern은 문서화된 `plugin-data/tern-desktop-pet/kv.json`의 소유자·일반 파일·경로·내용 hash·metadata를 읽어서만 기존 연결을 검증합니다. macOS 기본 root는 `~/Library/Application Support/Tern`이고 `TERN_CONFIG_DIR`은 config/state 모두를 바꿉니다. canonical 연결이 손상되면 legacy 키로 대체하지 않습니다. 실제 저장된 경로가 없으면 Tern 앱 설치나 ambient 환경만으로 plugin을 설치하지 않으며 native는 KV를 직접 쓰지 않습니다. 이미 현재 대상인 경로는 재설치하지 않고 실제 live binding으로 연결을 관찰합니다. 새 연동 설정은 별도의 명시적 요청에 따라야 합니다.

Brew의 정당한 재서명·relocation SHA는 원본 공개 metadata 및 허용된 resource/signing derivation과 실제 성공·quiescent 관리자 결과가 검증된 경우에만 별도 actual candidate로 기록합니다. 원래 승인 plan은 바꾸지 않습니다. 보존 작업의 forward delivery도 옛 journal hash·실제 현재 소유자/이미지·CLI/package/KV·현재 runtime의 Stop generation에 별도로 묶습니다. 새 private `*.runtime-start.json`은 옛 승인을 꾸미거나 재실행하는 증거가 아니며, 이후 사용자 Stop은 자동 동작 권한을 취소합니다.



### 표시 상태 (presentation)

```text
desktop-pet presentation get
desktop-pet presentation set (--visible on|off | --passthrough on|off | --alpha-passthrough on|off | --bubble-visible on|off | --bubble-placement above|below|left|right|auto | --scale NUMBER) [서로 다른 필드 추가 가능] [--expected-revision N] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet presentation reset [--expected-revision N] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet presentation status OPID --instance ID
```

`set`에는 최소 한 개의 절대값 필드가 필요합니다. `--scale`은 유한한 절대 렌더러 배율이며 `bigger`/`smaller`의 상대 조정이 아닙니다. `reset`은 캐릭터와 독립 말풍선의 위치만 초기화하고 표시 여부를 보존합니다. `get`의 `{ok:true,instance_id,snapshot}`에서 snapshot에는 `instance_id`, `revision`, `desired`, `effective|null`, `persisted|null`, `pet_window_visible|null`, `bubble_window_visible|null`, `pet_window_frame|null`, `bubble_window_frame|null`, `pending_reasons`가 있습니다. 프레임은 `{x,y,width,height}`이고 실제 창 상태는 목표보다 늦을 수 있습니다. 변경/status는 `{ok,instance_id,operation:{instance_id,operation_id,state,revision,target,native_applied,persisted,error},deadline_exceeded}`를 반환합니다. presentation 상태는 `accepted|pending|applied|superseded|persist_failed|rejected|shutdown|unknown`이며 초기 거절/불확실 전송에는 작업 객체 대신 `state:"rejected"`/`"unknown"`, ID와 오류가 나옵니다. `--expected-revision`은 CAS 조건입니다. 표시 변경은 **런타임 먼저** 진행되므로 네이티브 적용과 정확한 대상의 저장 성공을 분리해 확인합니다. `persist_failed`를 네이티브 변화로 감추거나 다른 저장으로 이 작업을 인증하지 않습니다. 저장되지 않은 후보를 유령 저장값으로 취급하지 마십시오.
수락된 표시 변경이 한 배치에 모이면 표시 여부·클릭 통과·알파 클릭 통과·말풍선 표시·배치·배율 중 명시적으로 요청한 필드를 최종 정규화 장면에서 저장합니다. 같은 대상의 후속 no-op도 이를 잃지 않지만, 거절된 후보는 다음 말풍선 전용 저장에 섞이지 않습니다. 다른 전체 대상에 의한 기존 superseded 규칙은 그대로입니다.

### 환경 설정 (preferences)

`--observation-local`, `--observation-remote`, `--machine`, `--clear-machines`는 Herdr 어댑터가 등록한 옵션/불투명 키입니다. core는 어댑터 없이 이를 생성하지 않습니다.

```text
desktop-pet preferences get
desktop-pet preferences set [--language system|ko|en|zh-Hans|ja] [--theme warm_ivory|dusty_rose|moonlit_ink|custom] [--surface #RRGGBB] [--text #RRGGBB] [--muted #RRGGBB] [--border #RRGGBB] [--accent #RRGGBB] [--status-indicators on|off] [--menu-bar always|recovery_only] [--observation-host auto|PROVIDER] [--observation-local on|off] [--observation-remote on|off] [--machine ID ... | --clear-machines] [--expected-revision N] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet preferences status --instance ID --operation-id OPID
```

`set`에는 설정 하나 이상이 필요합니다. 반복 `--machine`은 카탈로그 ID 목록이며 `--clear-machines`와 충돌합니다. 미지/비활성 ID는 `unknown_machine` 등 타입이 있는 오류로 실패하므로 먼저 카탈로그를 확인하세요. 부분 색상은 저장 팔레트와 병합하고 읽은 revision으로 쓰기를 보호합니다. `--expected-revision`의 경쟁 변경은 `revision_conflict`로 적용 없이 실패합니다. `get`은 도메인 래퍼의 `operation.result`에 `revision`, `desired`, `persisted`, `effective`, `pending_reasons`, `status_item_visible`, `effective_locale`, 등록 어댑터의 `observation_catalog`를 담습니다. 카탈로그에는 `initialized` 및 머신 ID·라벨·enabled·status가 있습니다. 타입이 있는 스냅샷 키는 `language`, `bubble_appearance`, `show_status_indicators`, `menu_bar_mode`, `observation_host:"auto"|"PROVIDER"`, `observation_local`, `observation_remote`, `observation_machines`입니다. 현재 소스 `--observation-host`는 분리형/`=VALUE` 모두 Auto 또는 등록된 불투명 제공자 ID만 허용하며 `both`·대소문자 변경·빈 값·앞뒤 공백·오타를 프로필/소켓/저장소 접근 전에 거절합니다. wire patch도 엄격하며 관대한 이전 읽기가 새 변경 값을 허용하지 않습니다. host/local/remote/machines는 **저장 먼저** 한 거래로 처리하고 데몬 재시작 없이 적용합니다. Tern으로 바꾸면 Herdr 전용 제어를 숨기지만 저장된 범위 선택은 유지합니다. 저장 실패(`persist_failed`)는 이전 저장/런타임 설정을 유지합니다. 후속 다른 호스트 대상은 pending 작업을 `superseded`로 만들 수 있으며 이전 요청의 네이티브 적용 증거가 아닙니다. `committed:true`는 저장됨, `native_applied`와 pending 이유는 그 정확한 대상의 이후 UI 상태입니다. 생명주기 `settings`와 혼동하지 마세요.
CLI `--language`는 분리형/`--language=VALUE` 모두 **정확히** `system`, `ko`, `en`, `zh-Hans`, `ja`만 허용하며 오타·대소문자 변경·빈 값·앞뒤 공백은 프로필/소켓/저장소 접근 전에 거부합니다. 디스크의 기존 알 수 없는 언어값을 읽는 관대한 fallback은 유지됩니다. `system`은 OS의 선호 언어를 순서대로 확인합니다. 대소문자를 구별하지 않는 일본어 태그와 중국어 간체(`zh`, 명시적 Hans, CN/SG 지역)는 지원하며, 명시적 번체(Hant 또는 TW/HK/MO 지역, 단 명시적 Hans는 제외)는 다음 지원 언어로 넘기고 없으면 영어를 사용합니다. CLI `--machine`은 **전체 목록 교체**이므로 모든 ID가 현재 활성화되어야 합니다. GUI의 신뢰된 선택 변경만 저장된 누락/비활성 ID를 유지·제거하고 현재 활성 ID를 추가할 수 있으며 CLI 검사를 완화하지 않습니다. 조용한 상태에서 열린 색상 설정은 충돌/조합 상태에 따른 버튼 자격·라벨만 갱신하고 필드 초안·포커스·선택·실행 취소·색상 견본은 건드리지 않으며 창을 닫으면 갱신을 중단합니다.

### 세션과 에이전트 프롬프트

```text
desktop-pet sessions list --instance ID [--filter all|idle|working|waiting|completed|unknown|offline] [--limit 1..128]
desktop-pet sessions show --instance ID --source N --generation N --terminal ID
desktop-pet sessions prompt --instance ID --source N --generation N --terminal ID (--text TEXT | --file PATH | --stdin) [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet sessions status --instance ID --operation-id OPID
```

`list`는 `{instance_id,revision,filter,total,matched,status_summary,rows,next_cursor:null}` 전체 모음 JSON을 출력합니다. `--limit` 기본값은 32, 허용 범위는 1–128이며 **전체 행 한도가 아닌 페이지 크기**입니다. CLI가 128행 너머까지 모든 페이지를 수집하고 instance/revision/filter/개수를 검증합니다. 불일치 시 부분 결과를 성공으로 출력하지 않습니다. 각 행과 `show`는 `key:{instance_id,source_id,generation,terminal_id}`, `source_label`, `is_local`, `pane_id`, `availability`, `status`, `outcome`, `display_status`, `metadata`(제목, 에이전트, workspace/tab ID와 라벨)를 포함합니다. 원본 소스 소켓 경로, 작업 디렉터리, 워크트리 checkout/root 경로는 제외됩니다. `show`는 정확한 키로 보존된 오프라인 행도 읽을 수 있지만 프롬프트 가능하다는 뜻은 아닙니다. `prompt`는 살아 있는 적격 로컬 소스만 대상으로 하며 원격/읽기 전용/오래된/오프라인 세션을 대상으로 하지 않습니다. `--text`, `--file`, `--stdin` 중 하나만 선택합니다. 파일과 표준 입력은 **클라이언트가** UTF-8로 읽고 데몬에는 텍스트를 보냅니다. 원본 프롬프트에는 512 KiB 예산(클라이언트의 4096바이트 예약 후 최대 **520192 UTF-8 바이트**)과 별도 큰 요청 봉투가 적용됩니다. 일반 도메인 요청/결과 프레임 한도는 각각 16 KiB/64 KiB, 프롬프트용 봉투/큰 응답은 약 516 KiB/68 KiB입니다. `agent_prompted`는 상위 프롬프트 ACK만 의미합니다. 모델의 정확한 완료는 세션 상태/결과를 별도로 관측하십시오.
데몬의 각 `sessions list` 페이지는 일반 도메인 결과 64 KiB 한도와 별도로 **봉투·JSON 이스케이프·커서·마지막 줄바꿈까지 인코딩된 응답 전체 512 KiB**로 제한됩니다. `--limit` 이하에서 들어갈 수 있는 가장 긴 행 접두부를 반환하며 행 하나와 필요한 커서도 들어가지 않으면 행/메타데이터 절단이나 빈 연속 페이지 대신 한도 내 오류를 반환합니다. CLI의 여러 페이지 수집 결과 전체는 512 KiB를 넘을 수 있습니다.

읽기 전용 예시(반환된 instance와 행의 정확한 키를 직접 옮기십시오):

```sh
desktop-pet presentation get
desktop-pet sessions list --instance '<get에서 얻은 instance>' --filter all --limit 32
desktop-pet sessions show --instance '<row.key.instance_id>' --source '<row.key.source_id>' --generation '<row.key.generation>' --terminal '<row.key.terminal_id>'
```

### 대화문 (dialogue)

```text
desktop-pet dialogue list
desktop-pet dialogue get --target JSON --locale ko|en|zh-Hans|ja --slot KEY
desktop-pet dialogue set --target JSON --locale ko|en|zh-Hans|ja --slot KEY (--text TEXT | --file PATH | --stdin) [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue reset-entry --target JSON --locale ko|en|zh-Hans|ja --slot KEY [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue reset-character --target JSON [--baseline JSON] [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet dialogue status --instance ID --operation-id OPID
```

`--locale`은 정확한 정규 토큰 `ko`, `en`, `zh-Hans`, `ja`만 허용하며 대소문자 변경·빈 값·앞뒤 공백은 거부합니다. 언어별 대화문 override는 서로 독립적이며 팩 자체의 메타데이터를 번역하지 않습니다. 작성된 대화문은 팩의 소유이고 작성된 번역이 없는 경우 기존 fallback을 유지합니다.

`KEY`는 `idle|running|waiting|unknown|head_tap|body_tap|pet|completion_observed`입니다. `list` 결과는 `{"targets":[{"identity":{"target":{"kind":"character|external_assets","id":"…"},"reference":{"id":"…","revision":N}|null,"generation":N},"name":"…","locales":[…],"slots":[…]}]}` 형태입니다. `--target JSON`에는 **반환된 `identity` 전체를 불투명한 JSON 값으로** 전달하십시오. 내부 target ID만 전달하지 말고 별도의 `--ref` 옵션도 없습니다. 참조 팩 revision과 등록 generation이 오래된 소스를 구별합니다. `get`은 `{selection:{identity,locale,slot},authored:string|null,override:string|null,effective:string|null,baseline:{metadata_token:string,override_entry:string|null,target_overrides_token:string},active:boolean}`을 반환합니다. `authored`는 원본, `override`는 사용자 저장값, `effective`는 호스트 반응 기본 문구까지 고려한 실제 해석값입니다. `active`는 이 대상이 현재 런타임 캐릭터에 영향을 준다는 뜻입니다. `--baseline JSON`에는 반환된 **`baseline` 전체**를 넣고 `selection`/`target`만 넣지 마십시오. 생략하면 새로 읽은 뒤 단 한 번 CAS 변경하며 변경 자동 재시도/무조건 덮어쓰기는 없습니다. 항목 set/reset은 소스 `metadata_token`과 해당 언어·슬롯의 `override_entry`를 비교하므로 같은 캐릭터의 다른 항목 변경은 충돌하지 않습니다. 캐릭터 전체 reset은 소스 메타데이터와 해당 대상 모든 override의 `target_overrides_token` 해시를 비교하며 다른 캐릭터 변경은 충돌하지 않습니다. 소스 해시는 캐릭터 식별자, 참조 팩 revision/generation, 작성된 모든 언어의 내용을 포함합니다. 오래된 소스/항목/대상은 `metadata_conflict`, `entry_conflict`, `target_conflict`, `stale_target` 등의 코드로 실패합니다. `reset-entry`는 한 override, `reset-character`는 해당 캐릭터의 override만 지우며 팩 원본 대화문은 지우지 않습니다. 빈 문자열·공백만 있는 set은 항목을 비웁니다. 공백 외 내용은 원본 공백/줄바꿈/탭을 보존합니다. 대화문은 최대 **2048 UTF-8 바이트**이고 허용되지 않는 제어 문자는 거부합니다. 파일/표준 입력은 클라이언트가 읽습니다. 비활성 대상 저장은 `committed:true,native_applied:false,active:false`이면서 `applied`일 수 있습니다. 네이티브 false를 저장 실패로 해석하지 마십시오. 활성 저장은 네이티브 갱신을 기다리며 pending일 수 있습니다. 저장 우선 실패는 이전 override/런타임을 유지하며 유령 항목이 없습니다. CLI는 GUI 편집기 초안/선택을 지우거나 모달을 열지 않습니다.
`character(id)`의 저장 override는 같은 ID의 모든 작성 revision에 공유되지만 `--target`과 CAS는 정확한 작성 참조/generation을 지정합니다. `active:true`는 반환된 작성 revision 자체가 선택되었다는 뜻이 아니라 그 공유 대상이 현재 선택 캐릭터에 영향을 준다는 뜻입니다. @2가 선택된 동안 보존된 @1을 읽으면 @1의 원문/기준값과 `active:true`가 함께 나올 수 있습니다. @1 저장/초기화도 @2의 실제 말풍선에 반영될 수 있고, `native_applied:true`는 저장 성공만이 아닌 현재 렌더러와 저장된 공유 override의 실제 수락을 요구합니다. 정확한 작성 소스·활성 렌더러·동일 대상 override의 변경은 보류 중인 네이티브 증거를 supersede할 수 있지만 메타데이터 캐시 퇴출이나 다른 대상 변경은 그렇지 않습니다. GUI는 정확한 `(target, reference)` 선택을 보존하고 삭제된 revision도 사용 불가 상태와 초안을 유지하며 몰래 다른 revision으로 바꾸지 않습니다. 손대지 않은 첫 ready 편집 내용은 포커스 중에도 채우며 metadata 도착 전 실제 편집(원본 공백·조합 문자 포함)은 초안으로 유지합니다. 조합 종료 뒤 미뤄진 초기 채우기를 한 번 처리하되 이후 포커스·선택·실행 취소는 덮어쓰지 않습니다. 캐시된 metadata 오류는 자동 polling으로 재시도하지 않고 명시적 편집기 재열기/선택이나 새 `dialogue get`/읽기에서 한 번 재시도하며 진행 중/성공 결과는 합칩니다.

비파괴 예시(`identity`와 `baseline`은 현재 `list`/`get`에서 얻은 JSON만 사용):

```sh
desktop-pet dialogue list
desktop-pet dialogue get --target '<dialogue list의 identity JSON>' --locale en --slot idle
```

### 워크트리 제거

```text
desktop-pet worktree inspect --instance ID --source N --generation N --terminal ID
desktop-pet worktree remove --token TOKEN [--operation-id ID] [--wait SECONDS | --no-wait]
desktop-pet worktree status --instance ID --operation-id OPID
```

`inspect`에는 **명시적 네 요소 세션 키**가 필요하며, 살아 있는 로컬 연결 워크트리만 허용합니다. 메인 저장소/루트는 보호됩니다. 결과는 `{token,instance_id,expires_in_seconds:60,key:{instance_id,source_id,generation,terminal_id},workspace_id,pane_id,worktree:{repo_key,repo_root,checkout_path,branch:null,is_main:false,is_linked:true}}`입니다. 세션 목록과 달리 여기에는 삭제 전 검토할 정확한 checkout 경로가 노출됩니다. `branch:null`은 상위 정보에 브랜치가 없어 알 수 없다는 뜻이지 브랜치가 없다는 뜻이 아닙니다. 토큰은 로컬에서 새로 생성되고 60초 만료, 일회용, 확인한 대상에 고정되며 재시작/소스 변경 시 무효가 됩니다. 만료되면 다시 inspect하십시오. `remove`는 토큰 **하나로만** 대상을 지정합니다. 경로/workspace ID/force 옵션이 없으며 토큰 사용 시 식별자를 다시 확인합니다. generation 불일치/대상 변경은 실패합니다. `--force` 우회, 휴지통/실행 취소, 브랜치 삭제는 없습니다. 상위 `force:false`는 변경된 tracked/untracked 파일을 거절하지만 **ignored 파일은 삭제될 수 있습니다**. 브랜치는 남습니다. 자기 소유의 폐기 가능한 checkout에서만, ignored 파일까지 확인한 뒤 실행하십시오. 백엔드 제거 사이에는 CAS 간극이 있으므로 토큰 재확인이 외부의 동시 파일시스템 변경까지 보증하지는 않습니다.
`expires_in_seconds:60`은 inspect가 토큰을 발급한 **시점의 초기 유효 시간**이며, 캐시된 작업 status에서 새로 계산한 잔여 시간이 아닙니다. status 반복 조회로 토큰이 갱신되거나 연장되지 않습니다.

**파괴적 예시 — 본인 소유의 폐기 가능한 연결 checkout과 그 내용을 검토하기 전에는 실행하지 마십시오.** 꺾쇠 값은 명시적 자리표시자이며 첫 세션 자동 선택/자동 삭제 스크립트가 아닙니다:

```sh
desktop-pet worktree inspect --instance '<본인 소유 폐기 대상 instance>' --source '<본인 소유 폐기 대상 source>' --generation '<본인 소유 폐기 대상 generation>' --terminal '<본인 소유 폐기 대상 terminal>'
# 정확한 worktree.checkout_path, 저장소 루트, workspace, ignored 파일을 먼저 확인하십시오.
desktop-pet worktree remove --token '<검토한 inspect의 새 token>' --operation-id '<새 고유 operation ID>' --no-wait
desktop-pet worktree status --instance '<같은 instance>' --operation-id '<같은 operation ID>'
```

제거 초기 `result`는 `{target:{key,workspace_id,pane_id,worktree},acknowledged:false,final_observed:false}`입니다. 상위 ACK 뒤에는 `pending,committed:true,native_applied:false,acknowledged:true,final_observed:false`가 될 수 있으며 이는 checkout 삭제의 증거가 아닙니다. 올바른 소스/generation의 일관된 새 관측에서 **pane과 session이 모두 없음**을 확인해야 `applied`, `result.final_observed:true`, `observation`이 됩니다. 이것도 감시자 관측이지 **파일시스템 인증이 아니며** `native_applied`는 계속 false입니다. 상위 거절, 불명확한 전달, 감시자 부재, 만료, 데몬 재시작은 재전송 허가나 디스크 상태의 증거가 아닙니다. 물리적 삭제가 중요하면 checkout을 별도로 확인하십시오.

### 팩 명령 및 기존 경계

`pack list`, `pack import --path PATH`, `pack validate --path PATH`, `pack preview --path PATH --output PATH [--phase idle|running|waiting|unknown] [--time-ms N] [--reaction head_tap|body_tap|pet|completion_observed] [--reaction-age-ms N] [--hit-overlay]`, `pack export ID [--revision N] --output PATH`, `pack select ID`, `pack update ID --path DIR`, `pack restore ID --revision N`, `pack remove ID`, `pack status OPID`는 대화문 편집과 별개입니다. 변경 옵션은 `[--operation-id ID] [--expected-generation N] [--wait SECONDS | --no-wait]`입니다. **select/restore의 ID는 위치 인자**이며 `--id`가 없습니다. select에는 `--revision`이 없고 restore에는 필수입니다. `--expected-generation`은 CAS 보호입니다. 팩 작업 출력은 별도의 `{operation_id,state,committed,ui_applied,generation,error}`이고 상태에는 `accepted`, `preparing`, `applying`, `completed`, `failed`, `canceled`, `durability_unknown`, `committed_pending_apply`, `unknown` 등이 있습니다. `ui_applied`와 저장소 commit은 다릅니다. 데몬이 없으면 기본 팩 변경은 자체 오프라인 worker에서 동기 실행됩니다. 명시적 `--wait`/`--no-wait`는 **실행 중인 데몬**이 필요하며 몰래 시작하지 않습니다. 불명확한 연결 끊김은 재전송 대신 `pack status OPID`로 조사하십시오. 팩 준비/ACK와 세션 프롬프트 ACK 어느 쪽도 하위 에이전트 완료를 인증하지 않습니다.
`--no-wait`라도 팩의 첫 응답이 이미 실패 종료 상태이면 status 폴링 없이 종료 코드가 0이 아닙니다. `accepted`/`preparing`/`applying`만 대기 ACK입니다. 명시적 대기는 위의 ACK 이후 절대 기한을 따릅니다.
